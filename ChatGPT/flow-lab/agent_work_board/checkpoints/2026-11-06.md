# จุดต่อ — Agent Work Boarding W3 Systems
วันที่: 2026-11-06 (Asia/Bangkok)

สถานะ: บันทึกข้อสรุปการออกแบบหลังสำรวจ ยังไม่สร้างบอร์ดหรือเครื่องมือใหม่

## อ่านก่อนทำต่อ
บันทึกนี้ปรับข้อเสนอเริ่มต้นใน SURVEY_TH.md และ next_slice เดิม: ไม่เริ่มจาก reader รายรอบเพียงอย่างเดียว ให้เริ่มฐานความสัมพันธ์ของโค้ดจริง แล้วใช้เหตุการณ์ที่มีหลักฐานมาทาบตรวจสอบบนฐานเดียวกัน ผลสำรวจเดิมเป็นหลักฐานย้อนหลังตาม source_revision เดิม ไม่ใช่สถานะสดของรีโป้

## เป้าหมายที่ BBX19 ชี้แจง
- ใช้ค้นหาตำแหน่งเมื่อโค้ดมีปัญหา ระบบหยุด หรือเส้นทางกำลังปรับปรุง
- เป็นพื้นที่ให้มนุษย์ เอเจนท์ และระบบอ่านความสัมพันธ์/ความสามารถ การรับส่ง และการเปลี่ยนรูปที่ไม่เป็นเส้นตรง
- ช่วย BBX19 เรียนรู้โครงสร้างโค้ดภายใน เห็นจุดเลือก จุดตรวจ น้ำหนักการตัดสินใจ และส่วนที่ขยายได้ โดยมีหลักฐานรองรับ
- บอร์ดเน้นโค้ดที่ทำงานจริง เอกสารไม่เป็นขั้นใน execution flow แต่เปิดผ่านลิงก์อธิบายเหตุผล กฎ เจตนา และบริบทได้
- “ช่องว่าง” ใน Vertical Space คือพื้นที่แอคชั่น ใช้บอกว่าอะไรไปไหนและเกิดอะไร ไม่ใช่ช่องข้อมูลที่ยังสำรวจไม่ครบ
- 6 Gradation แสดงความสัมพันธ์/ตำแหน่งกลุ่มโฟลเดอร์ ช่วยรู้ต้นกำเนิดและปลายทาง แต่ต้องไม่ทำรายละเอียดภายในแต่ละชั้นหาย และไม่แปลงความลึกเป็นลำดับเวลา
- เชนเป็นแต่ละช่วงเหตุการณ์ที่ส่งต่อกัน ระบบเดียว เช่น E-CS, Cross-X, W3API เข้าร่วมหลายเชน หลายครั้ง และหลายบทบาทได้
- มีหลายกลไกเลือกสายงานตามความเหมาะสม ห้ามบังคับทุกงานให้ผ่านระบบเดียวหรือเรียงทุกระบบเป็นโฟลวตายตัว
- การแสดงเส้นทางที่เสนอแก้ต้องแยกจากทางที่ตั้งค่าไว้และทางที่มีหลักฐานเกิดขึ้นจริง การแก้ภาพไม่เท่ากับแก้ runtime
- กฎ สี สัญลักษณ์ และชื่อ ต้องอ่านในบริบทเจ้าของ ไม่สรุปความหมายจากสี/ชื่ออย่างเดียว

## บริบทการทำงานและขอบเขต
BBX19 ยืนยันว่าเลือก Public โดยตั้งใจเพื่อใช้สิทธิ/ทรัพยากร GitHub ภายใต้ข้อจำกัดจริง ไม่ให้แทรกงานเกี่ยวกับคนนอกหรือบังคับแยก public/private เป็นเงื่อนไขของบอร์ด ผู้ใช้ปัจจุบันคือ BBX19 เอเจนท์ และระบบภายใน W3 การอ่านไฟล์หรือ clone ไม่เท่ากับได้ความเข้าใจการทำงานร่วมกัน
วัฒนธรรม ความสัมพันธ์ โมดูลคู่ และ continuity เป็นส่วนของกลไกตรวจสอบและประสานงาน schema เป็นข้อกำหนดขั้นต่ำตามบริบท บอร์ดไม่เป็นเอกสารศูนย์กลางที่นิยามแทนทุกระบบ
บันทึกนี้ไม่อนุมัติเปลี่ยน visibility, merge, deploy หรือแก้เส้นทาง runtime

## คู่มือทำรอบถัดไป
1. ตรวจ refactor/v0.2, สาขางาน, PR #324 และ source revision ล่าสุดก่อนแก้ อย่าเขียนทับงานผู้อื่น; ไม่แตะ main และไม่ merge เอง
2. เลือกโค้ดจริงหนึ่งบริเวณ ทำหน่วยจุด/ความสามารถ แอคชั่น และความสัมพันธ์ พร้อม input/output, เงื่อนไข, caller/receiver และลิงก์ commit/path/symbol/line
3. แยกความสัมพันธ์ในโค้ด เส้นที่วางแผน/เลือกไว้ การเรียกจริง การส่งรับที่บันทึก และข้อเสนอปรับแก้ ไม่รวมเป็นสถานะเดียว
4. ทาบเหตุการณ์เก่าหนึ่งรอบเพื่อตรวจว่าตามเส้นกลับไปหาโค้ดและหลักฐานได้ โดยไม่ execute งานเก่าซ้ำ อาจเริ่มจาก paired handoff/history ที่สำรวจแล้ว
5. เก็บ unknown และขอบเขตของหลักฐานชัดเจน การไม่พบ receipt ไม่ใช่หลักฐานว่าระบบเสีย
6. ใช้เครื่องมือเดิมก่อน เครื่องมือใหม่เก็บ w3_tool_store/agent_workbench/tools/ ตามหมวด พร้อมคู่มือ ที่มา รุ่น และ license หากดัดแปลง xrea; ข้อมูลโครงการเก็บที่นี่
7. ทุกรอบอัปเดตคู่มือ status.json และ checkpoint ระบุผลที่เสร็จ หลักฐาน/การทดสอบ ข้อจำกัด จุดติด และขั้นถัดไป ส่งสรุปไทยพร้อมลิงก์

## งานค้าง
- รูปแบบข้อมูลบอร์ดและหลักการแสดงแอคชั่นยังต้องทดสอบกับโค้ดจริง
- ยังไม่มี HTML board, reader ใหม่ หรือการเชื่อม live runtime
- การควบคุม/แก้โฟลวผ่านบอร์ดยังเป็นความสามารถเป้าหมาย ต้องตรวจกลไกเจ้าของแต่ละระบบก่อน
- หากรอบอัตโนมัติไม่มีสิทธิ์/สภาพแวดล้อมเพียงพอ ต้องบันทึกข้อจำกัดและรายงานตรงไปตรงมา ไม่อ้างว่าสำเร็จ
