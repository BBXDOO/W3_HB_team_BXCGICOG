## ลำดับความสำคัญ

- ขยายการตรวจสอบสถาปัตยกรรม native ชนิดข้อมูล และการเรียกทางอ้อม
- เชื่อมโยงข้อค้นพบแบบ static และข้อสังเกตขณะทำงานระหว่างชั้นต่าง ๆ ของแอปพลิเคชัน
- ปรับปรุงการเปรียบเทียบโค้ด managed ที่ถูกทำให้อ่านยากและการเชื่อมโยง native ที่ผ่านการตรวจสอบ
- ขยายความครอบคลุมด้าน process, protocol, filesystem, การเชื่อมต่อใหม่ และการเปรียบเทียบบิลด์
- ประเมิน provider และเป้าหมายเพิ่มเติมเมื่อขั้นตอนการทำงานของนักวิเคราะห์แสดงให้เห็นช่องว่างของความสามารถ

## เกณฑ์การรับเข้า

ความสามารถใหม่ต้องส่งคืนหลักฐานที่มีประโยชน์ผ่านขั้นตอน CLI/MCP ที่ใช้ร่วมกัน
รักษาข้อสังเกตและสิ่งที่ยังไม่ทราบไว้ และระบุขอบเขตอำนาจจริงและข้อจำกัดของวงจรชีวิต
agent ประกอบการทดลองด้วยคำสั่ง สคริปต์ และเซิร์ฟเวอร์ fixture ทั่วไป
ส่วน orchestration แบบกำหนดเองต้องมีความจำเป็นที่แสดงให้เห็นได้

คำกล่าวอ้างเกี่ยวกับ provider และแพลตฟอร์มต้องมี
[ช่องทางการตรวจสอบจริง](testing.md#real-toolchain-verification-lanes) ที่สอดคล้องกัน
ดู [การออกแบบเครื่องมือ](tool-design.md) สำหรับการเลือกขอบเขตเครื่องมือ และ
[ความหมายของ Ghidra](ghidra-provider.md) สำหรับสัญญา deep-provider ที่มีอยู่

การตั้งค่ายังคงเป็นแบบเพิ่มเติม ใช้เครื่องมือที่มีอยู่ซ้ำ และต้องได้รับอนุมัติสำหรับการเปลี่ยนแปลงการกำหนดค่าและการติดตั้ง Hopper ที่เปิดเผยไว้
ตัวเลือกตัวติดตั้งเพิ่มเติมต้องมี toolchain ที่นำไปใช้งานแล้วและขอบเขตที่ชัดเจน
การตั้งค่าจะไม่ติดตั้งหรืออัปเกรด runtime หรือ dependency ที่ไม่เกี่ยวข้อง
