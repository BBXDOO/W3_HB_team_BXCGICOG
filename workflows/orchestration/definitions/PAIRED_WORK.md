# คู่งาน: ผู้เดินงานและผู้ตรวจ

กติกาตามคำขอ BBX19 วันที่ 2 พฤศจิกายน 2569 — นำมาใช้ใน Origin collaboration และเครื่องมือ artifact_handoff

หนึ่งคู่งานมี **ผู้เดินงาน/ผู้ส่ง** และ **ผู้ตรวจ** เป็นคนละหน่วย
ผู้รับเป็นอีกบทหนึ่งและอาจเป็นฝ่ายเดิมในช่วงถัดไปได้ คู่และเส้นทางเปลี่ยนตามงาน
ไม่บังคับให้ทุกระบบผ่านสายเดียวกัน และงานหยุดได้เมื่อส่งมอบตามเงื่อนไขครบ

## ทุกการส่งและรับ

1. บันทึกจุดเริ่มก่อนทำงาน: คำขอ/รหัสคำขอ วิธีทำหรือรายการปฏิบัติ และลายนิ้วมือข้อมูลเข้า
2. ก่อนส่ง ตรวจหลักฐานจริงและบันทึก sender, reviewer, recipient, checks
3. ข้อสงสัยใช้หมายเหตุ `kind: doubt` ข้อผิดพลาดชัดเจนใช้ `kind: error`
   ทุกข้อมี id, owner, meaning และหลักฐานประกอบ
4. ใบส่งแนบหมายเหตุและคำชี้แจงทั้งหมด แล้วผู้รับอ่านใบและตรวจลายนิ้วมือหลักฐานอีกครั้ง
5. ใบถัดไปอ้างใบก่อนหน้าไว้ ทั้งข้อความหมายเหตุเดิมและคำชี้แจงคงอยู่ครบ

ใบส่งเป็น `w3.paired_handoff/1` ส่วนรายงานย้อนกลับเป็น `w3.paired_audit/1`
`host-origin-intake-verifier` และ `host-artifact-verifier` คือเครื่องมือตรวจภายใน host
ไม่ใช่โมดูล AI เพิ่มขึ้นมา ผู้ตรวจคู่ในงานจริงยังระบุชื่อโมดูลแยกจากผู้เดินงาน

## ก่อน Orchestration สรุปงาน Origin

อ่านหลักฐานจุดเริ่ม ใบส่งแต่ละช่วง หลักฐานที่อ้างถึง และหมายเหตุทุกข้อ
ตรวจความต่อเนื่องของใบ ลายนิ้วมือ และการคงหมายเหตุเดิม
รายงานแนบ `notes`, `explanations`, `note_review` และ `explanation_requests` เสมอ
แม้ไม่พบความขัดแย้งหรือไม่มีหมายเหตุ รายการเหล่านี้ก็ยังอยู่ในรายงาน

ผู้รับผิดชอบสามารถแนบคำชี้แจง **ทำอะไร / ทำแบบไหน / เพราะเหตุใด** ในคำขอ Origin รอบถัดไป:

```json
{
  "handoff_notes": [
    {"id": "note-001", "owner": "ChatGPT", "kind": "doubt", "meaning": "ขอบเขตที่ยังไม่ทราบ"}
  ],
  "note_explanations": [
    {"note_id": "note-001", "owner": "ChatGPT", "what": "อ่านไฟล์", "how": "ตรวจหลักฐานในพื้นที่", "why": "ตรวจตามขอบเขตคำขอ"}
  ]
}
```

สองรายการนี้อยู่ใน `payload` ของคำขอเดิมที่รับผ่านช่องทาง Origin ที่ได้รับสิทธิ์
ต้องยกหมายเหตุเดิมมาครบ คำชี้แจงอ้างผู้รับผิดชอบตรงกับหมายเหตุ
คำชี้แจงเป็นข้อมูลที่เจ้าของเสนอ (`verified: false`) ไม่ใช่การรับรองตัวตนหรือความจริงด้วยชื่อผู้เขียน
ผู้ส่งที่ได้รับสิทธิ์ต้องรับผิดชอบที่มาของคำชี้แจง กติกานี้ไม่สร้างระบบยืนยันตัวตนใหม่
คำชี้แจงไม่ลบหมายเหตุและไม่ทำให้หลักฐานที่ผิดกลับผ่านโดยอัตโนมัติ

## เมื่อพบข้อผิดพลาดชัดเจน

เก็บรายงานเต็มก่อน แล้วหยุดผลที่ยังตรวจไม่ผ่าน
Orchestration ใช้รายการความสามารถ/สิทธิ์อ่านจริง เลือกผู้ตรวจใหม่ที่ต่างจากผู้เดินงานและผู้ตรวจเดิม
บันทึกเหตุผลคัดเลือก/ปฏิเสธ ถ้าไม่มีคู่ที่พร้อมให้ระบุ `BLOCKED_NO_CAPABLE_PAIR`
การเลือกคู่ใหม่ไม่รันงานซ้ำอัตโนมัติ งานเดิมและผลที่เกิดแล้วไม่ถูกทับ
ผู้เดินงานยังเป็นเจ้าของงานเดิม ผู้ตรวจใหม่ต้องตรวจงานที่แก้แล้วก่อนส่งมอบ
การเปลี่ยนผู้เดินงานด้วยต้องมีความสามารถทำงานนั้นจริง จึงไม่ย้ายงานผลิต Cast ไปให้ผู้ที่ทำได้เพียง file_review

เมื่อระบุหน่วยที่ผิดได้จากหลักฐาน บันทึกข้อผิดพลาดในพื้นที่หน่วยนั้น `/notes`
Origin ใช้ `<module>/notes/` ส่วน Cast ใช้ `modules/Cast/notes/`
แต่ละเหตุการณ์เป็นไฟล์ใหม่และอ้างรายงานเต็มไว้ เพื่อใช้ปรับปรุงตนเอง
กรณีหลักฐานเปลี่ยนระหว่างทางแต่ยังระบุผู้เปลี่ยนไม่ได้ ให้รายงานข้อผิดพลาดและเปลี่ยนคู่ตรวจได้
โดยไม่กล่าวโทษหน่วยใดจากการคาดเดา

## ขอบเขตที่รับรอง

- ใช้กับ Origin intake/collaboration และ artifact_handoff ที่เชื่อมในรอบนี้
  ตัวส่งงานอื่นต้องเรียก protocol นี้ก่อนจึงมีหลักฐานคู่งานแบบเดียวกัน
- Origin เก็บ intake ก่อนเกิดผล ไม่แต่งจุดเริ่มย้อนหลังให้ใบงานเก่า หากขาดจุดเริ่มจะไม่รับรอง trace ครบ
- ตรวจโครงสร้างและไฟล์ภายในที่อ้างไว้ ไม่รับรองความหมายทั้งหมดหรือบริการภายนอก
- ใบส่งและลายนิ้วมือเป็นหลักฐานภายใน host ไม่ใช่ลายเซ็นเข้ารหัสของแต่ละโมดูล
- Cast เปรียบเทียบไฟล์ที่รับตรวจและ IDP กับค่าก่อนเริ่มของ host ณ จุดตรวจ
  ไม่ใช่ตัวเฝ้าดูทุกการเขียนทั้งรีโป้ และไม่ตรวจพบการเปลี่ยนแล้วคืนค่าระหว่างจุดตรวจ
- การรับรองทางเทคนิคยังแยกจากการอนุมัติขั้นสุดท้ายของ BBX19

## การผูกความรับผิดชอบหลังรีวิว

Origin host คืน `receipt_sha256` หลังเขียนใบปฏิบัติงาน และเครื่องมือตรวจคำนวณซ้ำก่อนเชื่อมผู้ผลิตกับผลนั้น
จะบันทึกความผิดจาก metadata ให้เจ้าของได้เฉพาะผลที่รอบนั้นสร้าง/แก้จริงและ hash ปัจจุบันยังตรงกัน
ไฟล์ที่เพียงอ่าน ไฟล์ที่ถูกเปลี่ยนภายหลัง หรือใบที่ยืนยันที่มาไม่ได้ ยังคงมีข้อผิดพลาดในรายงาน แต่ไม่ระบุผู้กระทำจากการคาดเดา
intake เก็บเฉพาะรายการ metadata ของคำสั่ง ไม่คัดลอกเนื้อหา old/new ของการแก้ไฟล์
คำชี้แจงที่เพิ่งเพิ่มต้องถูกส่งในใบใหม่ก่อน audit จึงจะรับรองว่าแนบถึงปลายทางแล้ว
